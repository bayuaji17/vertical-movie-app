# Repository instructions

This is a Bun workspace with two apps: `apps/api` (Elysia) and `apps/web` (TanStack Start), plus shared packages under `packages/`. Keep repository instructions in this root `AGENTS.md` and project documentation under the root `docs/` directory. Read `docs/README.md` and the relevant app's source and package scripts before changing behavior.

- Use Bun for installs, scripts, builds, and production runtime. The root `package.json` declares the required Bun version. Run workspace tasks from the repository root with `bun run dev`, `bun run build`, `bun run check-types`, and `bun run lint`; filter with `--filter=api` or `--filter=web` when appropriate.
- Prefer Bun native APIs when they meet the requirement and work with the chosen stack. For PostgreSQL with Drizzle, evaluate the Bun SQL driver; for Cloudflare R2 or S3-compatible media storage, evaluate Bun's native S3 client. Verify compatibility before adding an alternative dependency.
- Use PostgreSQL for the durable media job queue and FFmpeg for transcoding. Keep worker code in `apps/api` and run FFmpeg through a Bun subprocess outside HTTP requests and database transactions.
- Keep API code in `apps/api` and web code in `apps/web`. Add shared packages only when both apps actually need shared code. Do not hand-edit `apps/web/src/routeTree.gen.ts`.
- For API work, read and follow `docs/guides/api-development.md`: use Eden Treaty with a type-only API contract, preserve Elysia method chaining and inferred route types, respect lifecycle order and plugin scope, and apply admin authorization only to private routes. Keep handlers separate from domain logic and infrastructure dependencies explicit. Create the documented target folders only as their module tasks need them.
- Use Bun's native `bun:test` and `bun test` for API unit tests. Keep behavior tests beside their modules, inject external dependencies, and test Elysia HTTP behavior through `app.handle(new Request(...))` without opening a port. Keep tests requiring real PostgreSQL/storage/FFmpeg in the separate integration suite described in `docs/guides/api-development.md`.
- Better Auth is owned by `packages/auth` (`@repo/auth`). API code imports `@repo/auth/server`, web code imports `@repo/auth/client`, and shared types use `import type` from `@repo/auth/types`. Keep server configuration and secrets out of the client entry point.
- Follow the Agile workflow in `docs/guides/development-workflow.md`: break modules into user stories and small tasks with acceptance criteria, dependencies, and validation evidence. Use `docs/templates/task.md` when documenting a module's backlog under `docs/tasks/`.
- Keep env samples in `apps/api/.env.example` and `apps/web/.env.example`; document active and planned variables in `docs/guides/environment.md`. Local env files are ignored. Only public configuration uses `VITE_*`; database, auth secrets, and storage credentials belong to API configuration.
- Keep repository skills in the root `.agents/skills/`, agent symlinks in the root `.commandcode/skills/`, and installation metadata in the root `skills-lock.json`. Run each skill's application commands from the app that owns the relevant configuration.
- Use the installed `videojs` skill when working on video or audio in this project. For version-matched installation instructions, run `bunx --bun @videojs/cli agents init --method shadcn --framework react` from `apps/web`; use `--framework html` for plain HTML. The command only prints instructions. Read the skill and the installed player's bundled docs before implementing or changing playback.
- `bun run check-types` covers both apps and `@repo/auth`; `bun run build` builds both apps. The auth package exports TypeScript source directly, so its consumers compile it without a separate package build. `bun run lint` currently covers only `web`, because the API and auth package have no lint script. After changing scripts or package dependencies, run `bun install --frozen-lockfile` and the relevant checks.
- After completing implementation, run existing tests relevant to the change, `bun run check-types`, available lint scripts through `bun run lint`, and `bun run build`. Resolve failures before reporting completion and record the commands/results. When backend schema changes, generate/review migrations and apply pending migrations to the configured local development database with `bun run --cwd apps/api db:migrate`, then verify the journal/schema and preservation of existing data. Integration tests must keep using dedicated test databases. Production migrations remain part of an explicitly authorized rollout.
- Name branches with the existing purpose prefixes: `feat/<slug>` for features, `fix/<slug>` for fixes, and `chore/<slug>` for maintenance, including documentation organization. Do not use a tool-name prefix unless the user requests it.
- Commit each completed task separately after its acceptance criteria and relevant checks pass. This user-approved workflow authorizes local task commits without asking again; do not wait to bundle a whole module. Stage only the task's changes and required documentation, preserve unrelated work, and use a Conventional Commit message identifying the task ID. If a check or commit hook fails, fix it before closing the task and never bypass the hook. Record the resulting SHA and checks in the task/plan ledger, normally in the next task's documentation update; do not invent a self-referential commit SHA. Push, PR, merge and deployment still require their own authorization.
- Husky runs documentation, lint and type checks before commits; Commitlint checks Conventional Commits messages in `commit-msg`. Preserve existing worktree changes and keep generated `dist/`, `.output/`, and `.turbo/` files out of commits.
- Update `docs/README.md` when repository structure, runtime commands, or documentation ownership changes. Put new project documentation in the root `docs/` folder rather than creating app-specific docs folders.

## Documentation rules

- Keep agent/process instructions in this root `AGENTS.md`. Start each task from `docs/README.md` and read the relevant canonical specification, guide, runbook and backlog. Installed/vendor instructions and generated design assets keep their own formats.
- Keep `docs/README.md` as the documentation index and the only Markdown file directly under `docs/`. Root `README.md` remains the quick start; link to detailed guides instead of duplicating them. Use the categories below; do not create app/package documentation folders or new categories for a single task.

| Category                | Ownership                                                                               |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `docs/product/`         | PRD and approved product/business rules                                                 |
| `docs/architecture/`    | System architecture, data models and interface contracts                                |
| `docs/guides/`          | Development workflow, API conventions and environment setup                             |
| `docs/operations/`      | Active runbooks, commands, migration/recovery and operational limits                    |
| `docs/plans/<feature>/` | Feature-specific repository context, implementation plan and decision/execution history |
| `docs/tasks/`           | One backlog per module with stable story/task IDs, acceptance criteria and evidence     |
| `docs/templates/`       | Reusable documentation templates                                                        |
| `docs/design/`          | Canonical design system, prompts and related visual/export artifacts                    |

- Use lowercase kebab-case for new folder/Markdown names, except index files named `README.md`. Existing generated design filenames such as `design-system.colors.md` retain their generator format. New feature planning uses `docs/plans/<feature>/repository-context.md` and `implementation-plan.md`; inspect the relevant code at a recorded commit SHA, write context before the plan, and recheck freshness before implementation.
- Maintain one canonical document per subject. Update it in place when behavior, commands, contracts or decisions change; do not create numbered/session copies, root-level context/plan files, or a new report for every development turn. Keep lengthy task evidence in the module backlog and execution history in the feature plan. Link from specifications/guides to that evidence rather than copying it.
- State the status and date for new specifications/plans or material decision updates. Distinguish proposed, approved, implemented and verified behavior. Record who approved a product decision; do not infer production readiness from local tests or merge status. Preserve historical evidence, its date/base SHA and material limitations; identify it as history when it differs from the current implementation.
- Active instructions/commands belong to root `AGENTS.md`, guides and runbooks; product/data/API behavior belongs to the approved specifications and current code. Historical plans and old evidence do not override current instructions. Resolve a conflict by checking the current code and user-approved decisions, then update the affected canonical documents together.
- Use repository-relative paths in prose/code spans and file-relative destinations in Markdown links; add a section anchor when useful. When renaming a document, update incoming/outgoing links, source comments/env-sample references and the index in the same change. Preserve immutable external commit links. Keep secrets, database backups, temporary logs and build caches out of documentation.
- Update `docs/README.md` whenever adding, moving or changing ownership/status of a canonical document. Keep it as navigation and a concise current overview; detailed commands/contracts/results stay in their owners. Use `docs/templates/task.md` for module tasks and record only commands/results actually observed.
- Run `bun run docs:check` after documentation or instruction changes and before reporting completion. It validates category/name rules, local links/anchors and retired documentation paths; the commit hook also runs it. Format changed Markdown with the installed Prettier and run `git diff --check`. Documentation-only changes require these checks; script/dependency/runtime/schema changes also require the existing applicable quality gates above.

# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": false` in the root `turbo.json` or `turbo.jsonc` to opt out; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.
